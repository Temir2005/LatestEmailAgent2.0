# clinic-agent

Агент для переписки с медицинскими клиниками. Разбирает почту на тематические
цепочки, даёт сводку по каждой и — если контекста не хватает — спрашивает,
вместо того чтобы угадывать.

## Как это устроено

Три уровня. ИИ работает только на верхнем.

```
письма ──► [1] техцепочки ──► [2] дела ──► [3] сводка + допрос
           RFC 5322,           LLM          LLM
           БЕЗ ИИ              merge/split
```

**Уровень 1 — технические цепочки.** Union-find по графу ссылок
`Message-ID` / `In-Reply-To` / `References`. Неупорядоченный приход писем
чинится сам: множества сливаются, когда появляется недостающее звено, и
порядок обработки на результат не влияет.

Для писем-сирот (клиника пишет из CRM новым письмом без `References`) есть
запасной путь: нормализованная тема + пересечение участников + окно по
времени. Он тоже детерминированный, но такая цепочка честно помечается
`heuristic` — чтобы не путать догадку с доказанной связью.

**Уровень 2 — дела.** LLM получает цепочки **целиком** и делает ровно две
вещи: объединяет несколько цепочек в одно дело (счёт от `noreply@` относится
к тому же приёму) и разделяет одну цепочку на несколько дел (в переписке
обсуждают и справку для налоговой, и продление полиса).

> Модель не может разорвать связь, доказанную заголовками — отдельные письма
> ей не выдаются, единица работы — цепочка. Заголовки — истина о связности,
> LLM — о смысле.

**Уровень 3 — сводка и допрос.** По каждому делу: клиника, тема, статус,
чего от кого ждут, дедлайн, следующий шаг, ключевые факты. Если уверенность
ниже порога — модель обязана задать вопрос, а не выбрать правдоподобный
вариант.

### Петля допроса

Не разовый вопрос, а цикл:

1. Классификация или сводка возвращает вопросы;
2. вопросы попадают в очередь;
3. `bun run clarify` показывает их, вы отвечаете;
4. ответ разбирается в **факт** — общий (профиль) или относящийся к делу;
5. профильные факты подмешиваются в **каждый** следующий промпт;
6. затронутые дела пересобираются с учётом ответа.

Пункт 5 — причина, по которой один и тот же вопрос не задаётся дважды.

## Хранилище и дозагрузка

Данные лежат в **PostgreSQL**, письма подгружаются **сами**.

```
        IMAP                     watcher                    PostgreSQL
   новое письмо  ──событие──►  схлопывание   ──вставка──►    emails
                 ──опрос────►  пересборка    ──────────►     threads
                 ──догон────►   цепочек                      cases (только по команде)
```

Демон `watcher.ts` держит соединение с ящиком открытым и узнаёт о новых
письмах тремя независимыми путями — потому что ни один по отдельности не
надёжен:

| Путь | Когда срабатывает | Зачем нужен |
| ---- | ----------------- | ----------- |
| событие IMAP (`IDLE`) | сервер сам сообщает | быстро, секунды |
| периодический опрос | раз в 5 минут | IDLE за NAT умирает молча |
| догон при подключении | при старте и реконнекте | забирает пришедшее, пока демон лежал |

Приходы **схлопываются**: пачка из двадцати писем поднимает union-find один
раз, а не двадцать. Дела демон не трогает — разбор стоит денег и запускается
человеком; веб покажет, что переписка изменилась, зелёной точкой в углу.

Почему Postgres, а не файл рядом: в базу одновременно пишут демон и веб, а
читает ещё и CLI. SQLite в WAL-режиме через границу контейнеров это делает
плохо — и делал: `sqlite3` из терминала сносил `-wal` из-под живого
соединения, и API падал с `disk I/O error`.

Попутно из этого следует:
- даты — `timestamptz`, а не строки; по ним ходит демон;
- поиск — `tsvector` с русской конфигурацией и GIN вместо FTS5, со стеммингом
  («анализы крови» находит «анализ крови»);
- `key_facts` и варианты ответов — `jsonb`, а не текст.

> **Переменная называется `CLINIC_DATABASE_URL`, а не `DATABASE_URL`.**
> Общепринятое имя часто уже экспортировано в профиле оболочки под совсем
> другой проект — и агент молча писал бы медицинскую переписку в чужую базу.
> Именно это здесь и обнаружилось при первом запуске.

Была файловая база от прошлой версии — переносится без потерь, вместе с уже
разобранными делами:

```bash
bun run migrate:sqlite            # data/clinic.db → PostgreSQL
```

## Провайдеры

Анализатор один: одни промпты, одни схемы, одна логика. Провайдер — сменный
бэкенд за интерфейсом в полсотни строк.

|                    | Anthropic                | Gemini                        |
| ------------------ | ------------------------ | ----------------------------- |
| Вызов              | `client.messages.create` | `POST /v1beta/interactions`   |
| Системный промпт   | `system`                 | `system_instruction`          |
| Схема ответа       | `output_config.format`   | `response_format.schema`      |
| Модель             | `claude-opus-5`          | `gemini-3.7-flash`            |

Gemini здесь **временно**, пока нет Claude-ключа: у него есть бесплатный тариф.

История диалога хранится у нас в SQLite и переигрывается провайдеру целиком
каждый ход. У Anthropic иначе и не бывает — API stateless. У Gemini есть
серверная многоходовость (`previous_interaction_id`), но мы ей не пользуемся
и ставим `store: false`: поведение провайдеров совпадает буквально, а
медицинская переписка не оседает на серверах Google на 55 дней.

Схемы объявлены один раз в консервативном пересечении двух диалектов JSON
Schema; адаптеры дочищают под себя, тест гоняет каждую схему через оба.

## Запуск

Нужен бесплатный ключ Gemini: [aistudio.google.com/apikey](https://aistudio.google.com/apikey).

```bash
bun install
cp .env.example .env      # и вписать GEMINI_API_KEY
docker compose up -d db   # PostgreSQL, том переживает пересборку
```

### Веб-интерфейс

```bash
bun run web        # → http://localhost:3001
```

Всё, что делает CLI, доступно мышкой: дела и сводки, карточка дела со всей
перепиской, вопросы агента с формой ответа, таблица технических цепочек
(видно, где связь доказана заголовками, а где собрана эвристикой), чат и
черновик ответа. Загрузка корпуса и разбор идут через Server-Sent Events —
в браузере виден прогресс, а не подвисшая вкладка.

Чат умеет искать письма естественным языком («последнее письмо от Иванова»),
показывать полный текст, добавлять найденную цепочку в указанное дело и готовить
новые письма. Отправка всегда требует отдельного нажатия «Подтвердить отправку»;
для Gmail используется тот же пароль приложения, что и для IMAP.

Если порт занят, сервер берёт следующий свободный и печатает адрес.
Явный `PORT=8080` не подменяется — там занятость это ошибка конфигурации.
Оформление — по брендбуку Alatau Advance Air Group.

`bun run web` сам поднимает демон дозагрузки как дочерний процесс — если
IMAP настроен и внешний демон ещё не работает (проверяется по пульсу в базе).
Ходить на вкладку «Источники писем» и жать «Синхронизировать» руками для
этого не нужно: новые письма попадают в базу сами, а вкладка «Цепочки писем»
обновляется по пульсу раз в 15 секунд.

### Демон дозагрузки

```bash
bun run watch      # держит IMAP открытым, складывает новые письма в базу
```

Отдельно запускать не обязательно — `bun run web` поднимает его сам (см.
выше). Пригождается, если веб не запущен, а фон нужен, либо в Docker, где это
отдельная роль (`worker`, см. ниже) — тогда встроенный демон в `web`
выключен переменной `EMBED_WATCHER=0`.

Настраивается переменными: `WATCH_FOLDER` (по умолчанию `INBOX`),
`WATCH_INITIAL_DAYS` (90), `WATCH_POLL_SECONDS` (300).

### Терминал

```bash
bun run sync --demo            # демо-корпус
bun run cases                  # дела со сводками
bun run case 1                 # карточка дела
bun run clarify                # ответить на вопросы агента
bun run chat --case 1          # диалог по делу
bun run draft 1                # черновик ответа
```

Живой ящик — дописать в `.env` и синкнуть:

```bash
# EMAIL_ADDRESS=вы@gmail.com
# EMAIL_APP_PASSWORD=пароль-приложения   ← не основной пароль!
bun run sync --imap --days 30
```

Пароль приложения для Gmail: [myaccount.google.com/apppasswords](https://myaccount.google.com/apppasswords).

## Docker

```bash
cp .env.example .env      # вписать GEMINI_API_KEY
docker compose build

docker compose up -d db web worker           # → http://localhost:3001

docker compose logs -f worker                # что делает дозагрузка
docker compose run --rm agent cases          # разовая команда в терминале
docker compose run --rm agent case 1
docker compose run --rm agent clarify        # интерактивно, спрашивает с клавиатуры
```

Четыре роли: `db` — PostgreSQL, `worker` — дозагрузка писем, `web` — интерфейс,
`agent` — разовые команды. Порты меняются переменными `WEB_PORT` и `PG_PORT`.

Данные живут в томе `pgdata` и переживают пересборку образа — внутри
контейнеров состояния нет. Папка `./mail` проброшена для `.eml`-архивов:
`docker compose run --rm agent sync --eml /mail`.

Keychain внутри контейнера недоступен — секреты только через `.env`.

### Если не хочется держать ключ в файле

Есть необязательный сервис секретов: отдельный процесс на Unix-сокете
`~/.clinic-agent/auth.sock`, ключи в macOS Keychain, наружу не торчит ни один
порт. Агент сначала смотрит в `.env`, потом — туда.

```bash
bun run auth login gemini
bun run auth status
```

Флаг `--provider gemini|anthropic` перебивает конфиг для одной команды.

## Демо-корпус — тест-фикстура

`bun run sync --demo` кладёт переписку с намеренно поломанным threading:

| Что заложено                                             | Что проверяет                       |
| -------------------------------------------------------- | ----------------------------------- |
| Запись на МРТ, корректные `References`, префикс `ОТВ:`    | базовый threading + нормализация    |
| Счёт от `noreply@` без `References`, другая тема          | объединение на уровне 2, не на 1    |
| Результаты анализов, цепочка рвётся посередине            | эвристика + пометка `heuristic`     |
| Одна цепочка, два разных дела                             | разделение на уровне 2              |
| «Подтвердите, пожалуйста» без контекста                   | допрос вместо угадывания            |

Ожидаемо на уровне 1: **10 писем → 5 цепочек**, четыре по заголовкам, одна
эвристикой.

## Реальный ящик: два слоя отсева

На живой почте медицинской переписки — единицы процентов, остальное рассылки
и уведомления. В разбор идёт не всё подряд:

**Слой 1 — массовые рассылки, детерминированно.** По заголовкам RFC:
`List-Unsubscribe`, `List-Id`, `Precedence: bulk`. Без ИИ, без чтения тел.
На тестовом ящике снял 120 писем из 192.

По адресу отправителя не фильтруем принципиально: клиники шлют счета и
результаты именно с `noreply@`, и такой фильтр выбросил бы половину нужного.
Это закреплено тестом.

**Слой 2 — отбор по темам, дёшево.** Модель видит только отправителя, тему
и даты — тела писем на этом шаге никуда не отправляются. Отсеивает уведомления
магазинов, банков и игровых сервисов, которые рассылками не помечены.

Итог на тестовом ящике: 192 письма → 44 цепочки → 5 медицинских дел.

## Тесты

```bash
docker compose up -d db   # часть тестов работает на настоящей базе
bun test
```

Тесты, которым нужна база, работают в отдельной `clinic_test` и пересоздают
её с нуля — рабочие данные они не трогают. Без поднятого Postgres такой тест
честно печатает «пропущено», а не делает вид, что прошёл.

Детерминированная часть проверяется без обращения к LLM: union-find
(неупорядоченный приход, транзитивность, фантомные звенья, окно, участники),
нормализация кириллических префиксов, схемы через оба адаптера, разбиение
демо-корпуса. Тест паритета провайдеров сам пропускается, пока доступен
только один ключ.

## Границы

- **Агент не отправляет писем.** Черновик сохраняется и печатается вместе с
  корректными `In-Reply-To` / `References` — отправляете вы, руками.
- Запуск локальный. Медицинские данные лежат в SQLite в открытом виде;
  `data/` и `.env` в `.gitignore`.
- Тексты писем уходят наружу — в Google при работе на Gemini, в Anthropic
  при работе на Claude. Для медпереписки это стоит понимать заранее.
